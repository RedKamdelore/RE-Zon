# Выпуск обновлений Re:Zon

## Каналы

| В приложении | Версия | GitHub Release |
| --- | --- | --- |
| Основное | `0.4.0`, `0.4.1` и т.д. | Обычный опубликованный релиз |
| Бета | `0.4.0-beta.1`, `0.4.0-beta.2` и т.д. | Опубликованный **pre-release** |

Бета получает бета-версии и более новые стабильные выпуски. Основное исключает prerelease. При смене канала более старая версия не устанавливается: пользователь остаётся на текущей до появления более новой подходящей. Черновики GitHub приложению не видны.

## Локальная сборка

На Windows с Node.js 22.12+:

```powershell
npm ci
npx tsc --noEmit
npm test
npm run dist
```

Команда генерирует выбранную иконку, собирает код, переносит production-зависимости в `release/atlas-stage`, создаёт NSIS-установщик и проверяет контрольные суммы и зависимости внутри ASAR. Используется локальная копия Electron из node_modules. Компоненты упаковщика при первом запуске скачиваются автоматически.

Результаты в `release/<version>/`:

- `ReZon-Setup-<version>-x64.exe` — установщик.
- Одноимённый `.exe.blockmap` — данные дифференциальной загрузки.
- `latest.yml` — метаданные GitHub updater.
- `beta.yml` — дополнительное имя метаданных для бета-выпуска.
- `SHA256SUMS.txt` — контрольные суммы артефактов.
- `win-unpacked/` — распакованная программа для диагностики.

Проверка скачивания без установки: `node scripts/smoke-update.cjs`. Скрипт раздаёт собранный установщик только через loopback-сервер, использует настоящий electron-updater, проверяет успешную загрузку и отклонение неправильной SHA-512. Пользовательские данные и установленная программа не затрагиваются.

## Публикация в GitHub Releases

Репозиторий должен оставаться публичным: `RedKamdelore/RE-Zon`. Токен GitHub в приложение не встраивается.

1. Обновите версию в package.json и package-lock.json. Например, следующая бета: `npm version prerelease --preid beta --no-git-tag-version`. Стабильная версия: `npm version 0.4.0 --no-git-tag-version`.
2. Соберите и проверьте выпуск. Обновите заметки об изменениях.
3. Сохраните исходники выпуска в репозитории. Тег `v<version>` должен указывать на соответствующий исходный код.
4. Создайте GitHub Release с этим тегом. Для `-beta.N` обязательно включите **Set as a pre-release**.
5. Приложите установщик, blockmap, все YAML-файлы из папки этого выпуска и SHA256SUMS.txt. **Имена файлов не изменять**: они записаны в метаданных.
6. Опубликуйте релиз. Проверяйте из установленной более старой версии. В текущей версии обновление на саму себя не предлагается.

Workflow `.github/workflows/windows-release.yml` после загрузки исходников на GitHub собирает артефакты на Windows. Ручной запуск создаёт downloadable artifacts. Push тега `v*` дополнительно создаёт **черновик** релиза и прикладывает файлы; окончательная публикация остаётся отдельным действием. Сам workflow ещё нужно отправить в удалённый репозиторий вместе с исходниками.

## Настройки и данные

Источник по умолчанию находится в `resources/updates.json` и задаётся в конфигурации сборки. Пользователь может изменить его в раскрываемом разделе «Источник обновлений». Принимаются только HTTPS-адреса без учётных данных и параметров.

Канал, автопроверка и источник сохраняются отдельно в `%APPDATA%/rezon/updates-settings.json`. Музыкальная библиотека и плейлисты не зависят от смены канала. Установка начинается только после нажатия кнопки пользователем; перед ней renderer завершает отложенное сохранение данных.

## Проверено для 0.4.0-beta.1

- TypeScript и production-сборка.
- 468 тестов, включая 7 сценариев контроллера обновлений.
- Установщик Windows x64, соответствие версии и SHA-512 в метаданных, наличие 33 production-пакетов.
- Настоящая загрузка собранного установщика через локальный тестовый источник и отклонение неверной контрольной суммы.
- Смена каналов и состояния интерфейса в браузере с имитацией IPC.

Установка с перезапуском поверх пользовательской программы и обновление с опубликованного GitHub-релиза ещё не проверены. Сертификат подписи Windows не настроен. Файлы текущего выпуска не опубликованы этой сборкой.
